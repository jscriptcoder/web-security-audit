# OWASP Juice Shop — source-only security review

Reviewed source: `C:\Users\User\Projects\web-security-audit-workspace\juice-shop`, package version **20.3.0**. Review date: **2026-10-29**. This is an intentionally vulnerable training application. Ratings describe consequences if its behavior were used with real users/data; they are not allegations of an unintended production incident.

## Method and evidence boundaries

The review followed HTTP middleware registration, generated Finale APIs, model validation/setters, custom routes, frontend consumers, shared security helpers, and deployment configuration. No application was started, no endpoint was requested, no exploit was executed, no dependencies were installed, and no external service was contacted. All regression checks below are **proposed**, not executed. Dedicated challenge answers, solutions, historical reports, skills, and neighboring output directories were not opened. Challenge checks/comments encountered inside application handlers were not treated as proof of exploitability.

All `path:line` anchors are relative to the source root above. They identify the reviewed source, not a running deployment. **High confidence** means an explicit unsafe source-to-sink flow or missing check is visible; **medium confidence** means third-party implementation or browser behavior still needs verification. There are no CVE claims based solely on version numbers.

**Gated** findings depend on `utils.isChallengeEnabled(...)`: `lib/utils.ts:153-185` considers challenge metadata, safety mode, Docker, Heroku and Windows; `config/default.yml:89` sets `auto`, while `config/unsafe.yml:2` disables safety restrictions. Per-challenge metadata was not opened, so this report does not assert that every gated branch is enabled on this Windows checkout or a deployment. Ungated flaws remain independently relevant. Generated API findings prove the registration and missing application controls; exact Finale serialization/update semantics were not runtime tested or inspected in installed dependencies.

## Principal conclusions

The strongest chains are SQL injection into authentication and product search; a signing private key present in source and publicly served infrastructure configuration; anonymous exposure of complete user models through memories; arbitrary roles during registration; cross-user access/mutation; unsafe JavaScript/XML/file-processing paths; and HTML trust bypasses. Authentication is fragmented between JWT middleware, signature-only checks, decode-only claims and a non-expiring cache. New chat functionality inherits these identity problems and delegates business policy to model instructions.

## Findings

### F01 — SQL injection in login
**Critical · high confidence · anonymous.** `server.ts:616` exposes login. `routes/login.ts:33` interpolates `req.body.email` into a SQL literal; hashing the password does not protect the email expression. Results feed account selection and token issuance at `:35-47` and `:18-25`. A crafted email can change the predicate and authenticate as a returned account. The ordinary result path still requests TOTP for a returned account with a nonempty secret, so this is not proof that every MFA account can be bypassed with a simple predicate change. UNION-shaped identities and precise SQLite payloads were not tested.

**Remediation:** parameterized queries or ORM equality predicates; validate scalar inputs. **Regression:** quoted and SQL-like emails remain data; wrong passwords never produce a session; repeat against MFA accounts.

### F02 — SQL injection in product search
**High · high confidence · anonymous.** `server.ts:622` calls `routes/search.ts:20-22`, which inserts `q` into two LIKE expressions and sends query results at `:63-70`. A 200-character limit does not isolate SQL syntax. This can expose data from the same SQLite database, including user authentication material (`models/index.ts:32-42`, `models/user.ts:70-111`). Actual result-column alignment and driver handling are untested; arbitrary stacked statements or OS execution are not claimed.

**Remediation:** bind LIKE parameters and separately handle literal wildcard semantics. **Regression:** quotes, comments and union-like strings cannot change result schema or disclose another table.

### F03 — Shared JWT private key is embedded and publicly exposed through infrastructure
**Critical · high confidence · anonymous where registered file routes are served.** `lib/insecurity.ts:21` embeds the RSA private key used by `authorize` at `:54` and deluxe HMACs at `:147-149`. The same visible key material is embedded in `infrastructure/terraform/networking.tf:171` (also `terraform/networking.tf:171`). `server.ts:268-285` serves infrastructure files without authentication; stripping annotation comments and `lib/terraformCustomization.ts:12-23` renaming do not redact keys. An observer can obtain signing material and construct identities/roles accepted by application verification. This does not require a JWT algorithm-confusion exploit. The TLS certificate resource also exposes its private key if deployed; actual certificate deployment is unverified.

**Remediation:** rotate keys, load deployment-specific secrets from a secret store, separate JWT and TLS keys, remove infrastructure secrets from public routes, and invalidate existing tokens. **Regression:** public file/config responses contain no private keys; tokens made with retired keys fail; secret scanning catches committed key material.

### F04 — JWT checks do not enforce a consistent token purpose or complete claim validation
**High · high confidence for application omissions; library acceptance unverified.** `lib/insecurity.ts:52` configures generic JWT authorization with only a secret. `:55` uses JWS signature verification, not JWT expiry/issuer/audience checks, and is used for role checks (`:152-170`) and MFA temporary/setup tokens (`routes/2fa.ts:20,115`). Login issues a signed pre-MFA token using the same key at `routes/login.ts:40-43`; routes such as user lists, product creation and feedback deletion require only generic `isAuthorized` (`server.ts:384-392`). They do not require a fully authenticated token purpose. Thus a password-stage token is structurally suitable for these gates before MFA completion. Old package pins (`package.json`, `express-jwt` 0.1.3 and `jsonwebtoken` 0.4.0) plus absent algorithm allowlists merit testing, but acceptance of `none` or RSA/HMAC confusion is **not independently established** here.

**Remediation:** one modern verifier with explicit algorithms, issuer, audience, expiry and token-purpose checks; separate short-lived MFA credentials from access tokens. **Regression:** reject expired, wrong-purpose, wrong-audience and unexpected-algorithm tokens at every authorization gate, especially generated APIs; a pre-MFA token must access only MFA verification.

### F05 — Session cache bypasses expiration and survives logout/password changes
**High · high confidence · possession of a previously accepted token.** `lib/insecurity.ts:70-90` stores tokens indefinitely; `:184-194` verifies only uncached tokens, and `appendUserId` at `:173-180` trusts the cache without expiry. Cookie profile routes and routes such as wallet/data export rely on that cache rather than `isAuthorized`. `frontend/src/app/navbar/navbar.component.ts:241-249` only deletes client storage, while password mutation handlers never revoke caches (`routes/changePassword.ts:51-56`, `routes/resetPassword.ts:44-46`). Tokens cached at login even retain the original user object rather than verified claim expiry. A copied token remains usable on cache-only routes after logout or password changes, and potentially indefinitely until process restart. JWT-protected routes may still reject expiry.

**Remediation:** enforce claims on every request and server-side session revocation/versioning; refresh identity from authoritative state and expire cache entries. **Regression:** logout, reset, password change and elapsed expiration invalidate the same token across header and cookie routes; stale password/role/TOTP snapshots cannot authorize actions.

### F06 — Passwords use fast unsalted MD5
**High · high confidence · database or response disclosure prerequisite.** `lib/insecurity.ts:41` is plain MD5; `models/user.ts:70-74` hashes passwords with it; login compares this hash at `routes/login.ts:33`. Hashes therefore support fast offline guessing and reveal equal passwords across accounts. Security answers similarly use a shared source-embedded HMAC key (`lib/insecurity.ts:42`, `models/securityAnswer.ts:42-45`), giving no secret-key protection against a source reader.

**Remediation:** salted adaptive password hashing, appropriate cost parameters and migration on login; replace knowledge-question recovery with high-entropy one-time recovery credentials. **Regression:** identical passwords produce different hashes; stored values verify through the password API, not MD5 equality; migrate old records safely.

### F07 — OAuth accounts have passwords deterministically derived from their email
**High · high confidence · existing account created by this flow.** `frontend/src/app/oauth/oauth.component.ts:29-36` registers an account using base64 of the reversed email; `:46-47` logs in with the same deterministic value. The server login (`routes/login.ts:33`) does not verify a provider assertion or require OAuth proof. Anyone knowing such an account's email can reproduce its local password. The flow also uses an implicit token response without state (`frontend/src/app/login/login.component.ts:148-149`) and accepts fragment tokens without binding to a pending login (`oauth.component.ts:71-79`), enabling login-session mixups subject to provider/browser behavior.

**Remediation:** perform validated authorization-code/PKCE exchange, bind state, map verified issuer/subject to an account, and give provider-only accounts no guessable local password. **Regression:** knowing email cannot authenticate; wrong-state and unsolicited callbacks fail; provider-only identities cannot use a derived-password fallback.

### F08 — Password change allows omitted reauthentication and puts secrets in request URLs
**High · high confidence · cached session required.** `routes/changePassword.ts:39` checks the current password only if supplied, then changes the password at `:51`. It reads new/current/repeated passwords from query parameters (`:14-17`); the frontend constructs those URLs directly (`frontend/src/app/Services/user.service.ts:53-55`). `server.ts:364` logs combined requests, and public log routes exist at `:301-303`. This permits a stolen session to change credentials without the current password and places plaintext passwords in logs and URL-bearing intermediaries. Header-based authorization means this finding alone is not a generic unauthenticated image-tag CSRF.

**Remediation:** authenticated POST with JSON body, required recent reauthentication, password redaction and revocation. **Regression:** absent/incorrect current password fails; no password appears in request URL or logs; new credentials work and old sessions are revoked.

### F09 — Complete user models expose password hashes and TOTP seeds
**Critical · high confidence · anonymous for memories; authenticated for other paths.** `server.ts:650` exposes memories without an auth gate; `routes/memory.ts:24-25` includes `UserModel` and serializes the result. The association exists at `models/relations.ts:77-83`, and `models/user.ts` has no default secret-exclusion scope. Memory owners' user fields include password hashes and `totpSecret`. Separately, login signs the complete user at `routes/login.ts:22-25`, MFA login at `routes/2fa.ts:33-47` signs the complete model wrapper, and ordinary mutations return whole models (`routes/changePassword.ts:56`, `routes/resetPassword.ts:46`, `routes/saveLoginIp.ts:33`). `routes/currentUser.ts:27-32` accepts arbitrary requested field names. JWT payloads are readable, not encrypted. Exposed seeds compromise the second factor of affected owners; account takeover also requires satisfying or bypassing the password stage. Actual populated memory owners and serializer output were not runtime observed.

**Remediation:** explicit public DTOs at every response/signing boundary, user-model secret exclusions by default, minimal JWT claims, protected TOTP storage, and rotate exposed credentials/seeds. **Regression:** recursively inspect memory responses, all JWT payloads, whoami field requests and mutation responses for forbidden password/TOTP fields, including joined models.

### F10 — Registration mass assignment permits privileged roles
**Critical · high confidence in source design · anonymous.** `server.ts:431-445` does not constrain registration fields; the challenge middleware search shows pass-through `next()` after checking role (`routes/verify.ts:52-56`). Finale exposes `UserModel` at `server.ts:504-528`. `models/user.ts:76-95` accepts customer, deluxe, accounting and admin values and persists them. Login then signs the selected role. No controller overwrites registration role with customer. This supports administrative/accounting privilege creation under Finale's ordinary model assignment behavior; no request was sent to verify package behavior.

**Remediation:** allowlist registration fields and assign role exclusively on the server; restrict internal model attributes at the API layer. **Regression:** registration attempts with admin/accounting/role-like nested fields create only customers, while privileged changes require a separately authorized operation.

### F11 — Generated APIs lack function-level authorization
**High · high confidence in registration · anonymous or any signed token depending on route.** Finale exposes CRUD for all listed resources (`server.ts:504-528`) without a global deny-by-default policy. Product PUT has its authorization commented out (`:391-394`), product POST requires any token, Users list/read require any token (`:386-390`), and Feedback DELETE only meets `isAuthorized` (`:384`, with only PUT denied at `:456`). Complaints list is likewise any-user (`:404`). `routes/authenticatedUsers.ts:12-30` returns all users' profile/role/IP/session details, protected only by generic auth at `server.ts:421`. Frontend AdminGuard (`frontend/src/app/app.guard.ts:48-60`) does not protect direct HTTP requests. This permits catalog tampering and cross-user administrative disclosure/actions, not arbitrary database-wide mutation.

**Remediation:** explicit per-resource/per-method permissions with role checks; avoid automatic CRUD for privileged resources. **Regression:** an anonymous/customer/admin matrix for each generated method; customer feedback deletion, complaint enumeration, and user enumeration fail; anonymous product updates fail.

### F12 — Generated APIs trust foreign keys and fail ownership checks
**High · high confidence in source design · mostly ordinary user.** Address PUT only appends the caller's `UserId` (`server.ts:473`) before generated ID-based update; it never scopes the existing address to that user. `models/address.ts:33-35` permits ownership changes, so this can overwrite/transfer another address. Complaint/Recycles/PrivacyRequest creation accepts client `UserId` (`server.ts:405,409,467`) without append/owner validation; their models contain assignable foreign keys (`models/complaint.ts:28`, `models/recycle.ts:30-34`, `models/privacyRequests.ts:31`). Feedback POST also accepts `UserId` (`models/feedback.ts:31`) without binding it to a session. Public SecurityAnswer POST lacks an authenticated owner binding (`server.ts:417-419`, `models/securityAnswer.ts:29-45`); it can establish recovery answers for a user lacking a record, although the unique UserId constraint prevents assuming overwrite of existing answers. Recycle reads (`routes/recycles.ts:11-17`, `server.ts:411`) are anonymous, ID-only and accept JSON arrays as IDs, exposing other users' pickup/association records.

**Remediation:** scope target queries by principal before updates; derive owner fields; validate related-object ownership; protect recovery-answer enrollment. **Regression:** two-user tests reject address overwrite/transfer and foreign-owner record creation; unauthenticated recycle reads and recovery enrollment fail; arrays/operator objects are rejected as IDs.

### F13 — Basket read, item modification, coupon and checkout lack owner scoping
**High · high confidence · logged-in user.** Authentication at `server.ts:379-382` does not establish basket ownership. `routes/basket.ts:18-19` reads by URL ID; `routes/coupon.ts:13-24` updates by ID; `routes/order.ts:34-35,50-51` checks out and empties by ID. `routes/basketItems.ts:68-79` checks stock but not the item's owner, and generated item GET/list/DELETE inherit only authentication. Foreign-key immutability hooks (`models/relations.ts:47,99`, `lib/noUpdate.ts:16-55`) do not prevent editing quantity or deleting an already foreign-owned item. An attacker can view another basket, alter its contents, attach discounts or consume it as their order; wallet deduction uses the caller's appended identity rather than proving ownership of the selected basket.

**Remediation:** resolve basket and items through the authenticated user's ID in every operation. **Regression:** two users cannot read/update/delete/checkout/apply coupons to each other's IDs; normal owner flows remain functional.

### F14 — Duplicate JSON keys bypass basket-add ownership validation
**High · high confidence · logged-in user.** `lib/utils.ts:188-199` preserves every key occurrence; `routes/basketItems.ts:21-33` collects all BasketIds. Authorization checks the **first** at `:37`, while persistence uses the **last** at `:40-49`. A body with the caller's basket first and another basket last satisfies one interpretation and writes the other. This is separate from missing ownership checks on existing items.

**Remediation:** parse once into a strict schema, reject duplicate keys, and use the same validated basket ID throughout. **Regression:** duplicate BasketId/ProductId/quantity keys are rejected before any mutation; test ordering and nested-key variants.

### F15 — Review author spoofing, cross-user changes and query-operator injection
**High · high confidence · anonymous creation; authenticated modification.** `server.ts:653` leaves creation public and `routes/createProductReviews.ts:23-28` stores the body-supplied author. `routes/updateProductReviews.ts:16-19` uses untyped body `id` as a query value, with `multi:true` and no author predicate. A scalar foreign review ID can change another author's message; an operator-shaped ID can broaden the query if MarsDB supports that operator. This compromises review integrity and feeds the data-export XSS chain in F20. Actual operator evaluation was not run.

**Remediation:** derive authors from verified principals, require scalar IDs, authorize against stored author IDs, and update a single matching record. **Regression:** anonymous author impersonation and foreign-user updates fail; object/array IDs cannot broaden updates.

### F16 — NoSQL queries evaluate attacker-built JavaScript expressions
**High · high confidence source sink; gated.** `routes/showProductReviews.ts:31-36` concatenates a URL ID into `$where`; the enabled branch only truncates it. `routes/trackOrder.ts:15-18` similarly inserts a URL ID inside a quoted JavaScript string. Both routes are public (`server.ts:637,652`), and collections use MarsDB (`data/mongodb.ts:7-10`). Predicate manipulation can select extra reviews/orders; the review module installs a blocking global sleep (`:17-25`), making CPU blocking an explicit reachable concern. Truncation is not syntax isolation. Arbitrary OS command execution or a particular sandbox escape is not claimed.

**Remediation:** ordinary typed field equality queries with no executable strings. **Regression:** JavaScript-shaped IDs are rejected or treated literally; collection selection and event-loop responsiveness stay bounded.

### F17 — Lossy email masking is used as an authorization identity
**High · high confidence · authenticated colliding account.** Orders store an email with every vowel replaced by `*` (`routes/order.ts:170`). `routes/orderHistory.ts:15-18` and `routes/dataExport.ts:21-33` use that masked value to select a user's orders; chat repeats the comparison at `routes/chat.ts:164-168`. Different valid emails can map to the same string. Registration only checks full-email uniqueness (`models/user.ts:56-68`), so account B can receive account A's matching orders without needing A's password.

**Remediation:** store and query immutable user IDs; apply redaction only to display fields. **Regression:** two deliberately colliding masked emails retain separate order histories, exports and chat access.

### F18 — URL-controlled text is explicitly trusted as HTML
**High · high confidence · victim visits a crafted client URL.** `frontend/src/app/search-result/search-result.component.ts:135-143` reads query `q` and calls `bypassSecurityTrustHtml`; its template renders `[innerHTML]` at `search-result.component.html:11`. No server request sanitization can protect this client-only path. Order tracking similarly trusts returned `orderId` (`track-result/track-result.component.ts:46-49`, `.html:9`); `routes/trackOrder.ts:21-23` reflects the supplied ID when no order exists (gated sanitization described in F16). Attacker HTML can run in the shop origin under browser execution rules, reaching script-readable credentials. No browser payload was exercised.

**Remediation:** interpolate text instead of bypassing sanitizer; use actual `<code>` elements with text content. **Regression:** malicious query/order strings render literally with no active DOM or event execution; ordinary searches/tracking still render.

### F19 — Stored user/product fields cross Angular's HTML trust boundary
**High · high confidence for email/product paths; gated persistence.** `models/user.ts:59-67` leaves email unsanitized in its enabled branch. `frontend/src/app/administration/administration.component.ts:69-74` embeds it into trusted HTML, rendered at `.html:26,113`. Public registration therefore supplies stored HTML to administrators. Product description similarly persists raw data in `models/product.ts:51-61`; F11 permits unprivileged modification. `search-result.component.ts:110-113` trusts it, the product dialog receives it through `product/product.component.ts:212-218`, and `product-details/product-details.component.html:18` inserts it as HTML. `routes/saveLoginIp.ts:18-32` also stores a caller-controlled header that `last-login-ip.component.ts:35-40` trusts from a later login token, rendered at `.html:10`; this IP path is primarily same-account injection absent another way to set the victim's header.

Feedback has a similar sink in `administration.component.ts:92` and `about/about.component.ts:117-126`, but `models/feedback.ts:43-49` does invoke a sanitizer. An actual bypass of the pinned sanitizer was not established, so feedback XSS is a follow-up, not an independently confirmed exploit in this finding.

**Remediation:** preserve text semantics end-to-end; remove trust bypasses; allow only constrained sanitized rich text if required. **Regression:** stored email, product and IP payloads cannot create active elements when other users view them; add sanitizer-specific feedback tests separately.

### F20 — Data export renders attacker-controlled JSON as active HTML
**High · high confidence · victim requests an export.** `routes/dataExport.ts:39-40,89-108` copies review messages into JSON text without HTML escaping. `frontend/src/app/data-export/data-export.component.ts:67-72` writes that JSON directly to a same-origin blank window using `document.write`. JSON stringification does not escape HTML tags; an attacker can use F15 to publish a message attributed to the victim or alter the victim's review. On export, executable HTML is interpreted in the new window, with same-origin access/opener access subject to browser popup behavior. The popup may be blocked; that does not remove the unsafe sink when it opens.

**Remediation:** offer a JSON download with an appropriate content type, or use textContent in a `<pre>`; do not write export strings as markup. **Regression:** a victim's export containing hostile review HTML remains inert text and cannot access the opener or token storage.

### F21 — Profile-image URL fetching allows SSRF and same-origin attacker content
**High · high confidence · cached cookie session.** `routes/profileImageUrlUpload.ts:18-30` passes an arbitrary imageUrl to server `fetch`, follows its normal redirects, and saves the response body into the publicly served upload directory. There is no scheme/host/IP allowlist, redirect destination check, timeout, response-size bound or media-content validation. A session can cause requests to server-reachable internal HTTP services and retrieve their response bytes through the saved image path. Internal reachability and any cloud metadata response remain unverified. The `.svg` extension is explicitly allowed at `:28`; attacker-hosted active SVG can be published under the shop origin when opened as a document (execution inside a normal image element is not assumed).

**Remediation:** deny private/local destinations after DNS resolution and each redirect, limit bytes/time, validate and re-encode raster images, and serve user content from an isolated origin. **Regression:** internal IPv4/IPv6, DNS changes and redirect chains fail; oversized/slow responses stop; SVG/script-bearing bodies cannot execute in the application origin.

### F22 — Profile username is evaluated as server JavaScript
**Critical · high confidence · authenticated account; gated.** `routes/updateUserProfile.ts:38` stores the requested username; model HTML filtering (`models/user.ts:47-53`) does not enforce a non-code grammar. `routes/userProfile.ts:57-65` extracts code from a `#{...}`-shaped username and calls direct `eval` in the Node process, then inserts its result into a Pug source string (`:73`) before compilation (`:90`). This is an explicit path to executing attacker expressions with application-process privileges when enabled. Filesystem access, environment confidentiality and service integrity are bounded by process permissions; no host escape or deployed execution was tested.

**Remediation:** remove evaluation entirely and compile a fixed template with escaped data locals. **Regression:** expression-shaped usernames are displayed as text, produce no side effects, and cannot alter template source.

### F23 — User-controlled image data is interpolated into CSP directives
**Medium · high confidence source flow · authenticated own profile.** `routes/profileImageUrlUpload.ts:35-36` persists the unvalidated URL even after fetching fails. `routes/userProfile.ts:91-99` concatenates `profileImage` directly into a CSP header before the intended script directive. A value containing semicolon-delimited policy text can alter directive parsing; duplicate-directive/browser behavior was not exercised. This weakens defense on an already dangerous profile template path, but is not alone proof of cross-user script execution.

**Remediation:** use a static CSP with approved image origins and a strict typed image URL; remove unsafe-eval where unnecessary. **Regression:** profile values containing directive separators cannot change response CSP; browser policy tests confirm scripts remain blocked.

### F24 — Cookie-authenticated mutations lack CSRF controls; whoami also exposes JSONP
**High · high confidence missing controls; browser-dependent reachability.** Profile updates/images and data-erasure POST authenticate with `req.cookies.token` (`routes/updateUserProfile.ts:17-38`, `profileImageUrlUpload.ts:21`, `profileImageFileUpload.ts:34`, `dataErasure.ts:74-88`). Form-urlencoded parsing is enabled at `server.ts:333`; no CSRF token or rejecting Origin/Referer check is registered. The origin check in updateUserProfile is merely challenge bookkeeping and does not block. Cookies are set without Secure/HttpOnly/SameSite options (`updateUserProfile.ts:42`, `lib/insecurity.ts:190`) and by script (`frontend/src/app/login/login.component.ts:110-113`). Cross-site mutation requires the browser to send the cookie; modern default SameSite behavior can block some cross-site POST cases, while same-site attacker origins or permissive deployment settings remain relevant.

`routes/currentUser.ts:54-58` also returns authenticated data as JSONP. With eligible cookies, another origin can load it as script and read selected user fields, including F09's unconstrained sensitive fields. Wildcard CORS (`server.ts:183-184`) alone is **not** evidence of credentialed cross-origin reads.

**Remediation:** explicit secure cookie policy, CSRF tokens and origin checks on cookie mutations; remove authenticated JSONP. **Regression:** cross-origin/sibling-origin form submissions fail, state is unchanged, callback parameters do not turn private data into executable JavaScript, and same-origin flows pass.

### F25 — ZIP extraction checks the project directory rather than the extraction root
**High · high confidence · anonymous; gated.** `/file-upload` has no auth requirement (`server.ts:335`). `routes/fileUpload.ts:27-35` resolves archive entry paths but checks `absolutePath.includes(path.resolve('.'))`, then writes the untrusted path under `uploads/complaints/`. Parent segments can escape that directory and overwrite writable files elsewhere inside the project. The substring check can also confuse similarly named sibling directories. Existing directory structure, platform paths and process write permissions bound the writable targets. ZIP entry sizes/count and aggregate expanded size are not capped; the compressed request limit at `server.ts:714` does not cap extraction output.

**Remediation:** resolve against a dedicated root, require containment by path components, reject absolute/traversal/symlink entries, safely create files, and bound count/expanded bytes. **Regression:** parent, absolute, backslash, sibling-prefix and symlink entries never write outside a temporary test root; expansion limits fail safely.

### F26 — XML external entities are enabled with host filesystem access
**High · high confidence · anonymous; gated.** `lib/xml.ts:19-22` registers host filesystem providers and `:35` enables NOENT and DTDLOAD. Uploaded XML reaches this parser through `routes/fileUpload.ts:77-83`; parsed output is included in an error, truncated to 400 characters on the success path. This enables reading parseable process-readable file content through external entities and returns at least an initial fragment, subject to parser behavior and valid entity content. Entity expansion also consumes process resources. The 2-second VM timeout is a mitigation for some CPU cases, not a filesystem boundary. Outbound HTTP XXE is not asserted because only filesystem providers were evidenced.

**Remediation:** disable DTDs/external entities, remove filesystem providers for untrusted input, cap document complexity and return generic errors. **Regression:** external-file entities disclose nothing; entity expansion is rejected before expensive work; legitimate supported XML remains usable.

### F27 — Request body is passed as template-engine options, including layout
**High potential impact · medium confidence · cached session.** `routes/dataErasure.ts:103-118` accepts a caller-supplied `layout`, applies a short substring denylist, and spreads the entire body into `res.render`. The fallback at `:123-126` still spreads the body when the gate is disabled, so disabling this challenge does not remove the unsafe option flow. HBS layout resolution can turn this into local-file/template disclosure; exact accepted paths, extension behavior and bytes exposed require validation against the installed HBS implementation. The gated callback returns only the first 100 rendered characters; do not equate this with arbitrary full-file reading in every configuration.

**Remediation:** explicitly select presentation locals; never accept layout/settings/cache/view options from requests; use a fixed layout. **Regression:** arbitrary layout and engine-option fields cannot influence file access in either gate state; a filesystem spy observes only intended templates.

### F28 — Memory uploads write unbounded files before authentication
**High · high confidence · anonymous.** `server.ts:338` runs `uploadToDisk.single('image')` before `security.appendUserId`. Its Multer configuration (`:720-739`) has no file-size limit, trusts the multipart MIME label, and writes to a public directory. Failed authentication occurs after the upload is stored; there is no cleanup in that chain. An unauthenticated sender can therefore fill storage with arbitrary large bodies labeled PNG/JPEG, even when the final HTTP status is 401. This differs from memory-storage complaint/profile uploads, which have a 200,000-byte cap at `:714`.

**Remediation:** authenticate before parsing files; add per-file/request/account quotas, content validation and failure cleanup; store outside the public tree. **Regression:** unauthenticated uploads create no files; spoofed and oversized files fail with no residue; quotas and cancellation cleanup work.

### F29 — Synchronous attacker-controlled parsing/evaluation can monopolize the event loop
**Medium · high confidence source design; gated branches.** YAML uploads call `JSON.stringify(yaml.load(data))` in a 2-second VM context (`routes/fileUpload.ts:103-127`); B2B orders evaluate caller code through notevil with the same timeout (`routes/b2bOrder.ts:18-32`). The former is anonymous; B2B has only generic auth (`server.ts:447`). Repeated expensive requests can occupy the single event loop; memory expansion/stringification can exceed a byte cap even from small inputs. A VM timeout is not a global rate/concurrency/memory limit. No particular unsafe YAML tag RCE or notevil sandbox escape was established.

**Remediation:** parse data with safe schemas rather than evaluate code, cap complexity/output, isolate expensive processing in workers with hard resource budgets, and throttle. **Regression:** adversarial nested/aliased documents and long-running expressions cannot block normal requests or exceed bounded worker memory/time.

### F30 — Coupons are forgeable and expired campaigns trust a client timestamp
**High · high confidence · logged-in purchaser.** `lib/insecurity.ts:97-118` encodes month and discount with Z85 without a signature; decoding validates only a loose, unanchored pattern and current month. The number is not constrained to a business-approved maximum. `routes/coupon.ts:15-24` stores such values and `routes/order.ts:111-117,190-204` applies them. The alternative campaign path base64-decodes caller data and compares its timestamp to a historical campaign's `validOn`; it never compares the server's current date. A client can self-issue discounts or resurrect old campaigns. Encodings' formatting requirements affect accepted strings, not authenticity.

**Remediation:** server-stored unpredictable coupon IDs or authenticated, bounded claims; validate time against server clock, eligibility and redemption count. **Regression:** fabricated/modified/over-limit discounts and expired campaigns fail regardless of caller timestamp; valid discounts remain bounded and single-use as intended.

### F31 — Negative quantities violate checkout arithmetic
**High · high confidence · authenticated purchaser.** `routes/basketItems.ts:87-101` checks only upper bounds against stock and per-user limits. `models/basketitem.ts:39` has no positive-integer constraint. Negative quantities therefore pass these checks, and `routes/order.ts:80-81,93-107` subtracts them from inventory and multiplies them into prices/bonus points. If the final wallet total is negative, `:149-150` decrements by a negative amount, potentially increasing balance. The actual total depends on prices, delivery and mixed items; not every negative item guarantees net credit.

**Remediation:** enforce positive bounded integer quantity in request schemas and database/model constraints; reject nonpositive totals and validate stock again at checkout. **Regression:** negative/zero/fractional/oversized quantities fail through POST and PUT; inventory, prices and wallet never move in the wrong direction.

### F32 — Unsupported or missing payment modes bypass required payment checks
**High · high confidence · ordinary customer.** `routes/deluxe.ts:24-40` checks only the exact values `wallet` and `card`; any other value falls through to role upgrade and a new token at `:42-50`. Checkout similarly deducts funds only when `paymentId === 'wallet'` (`routes/order.ts:146-155`); other values, including missing values, proceed to order insertion at `:164-180`, with optional delivery defaulting to zero (`:119-131`). There is no server check that the non-wallet card/address is present, owned or valid. Impact is unpaid membership and orders in the application's simulated commerce model; no real payment processor loss was observed.

**Remediation:** a closed payment-method enum, required owned payment/address/delivery references, and explicit successful payment authorization before fulfillment/upgrade. **Regression:** omitted/unknown modes and foreign/nonexistent payment IDs fail without role/order changes; success requires an authorized payment result.

### F33 — Wallet credits rely on card existence rather than a successful charge
**High · high confidence · user with any stored card.** `routes/wallet.ts:23-28` checks that a caller-owned card exists, then increments balance by the caller's requested amount. No payment authorization, receipt, amount limit or idempotency key is required. `models/card.ts:38-59` validates only number/expiry shapes, so creation of a syntactically valid card supplies the prerequisite. This lets users mint arbitrary shop credit in this model, not charge or steal funds from a verified external card account.

**Remediation:** credit only from a verified server-side payment event with immutable amount/currency and replay protection; bound requested amounts. **Regression:** card existence alone cannot credit a wallet; failed or repeated payment events do not change balance; negative/invalid amounts fail.

### F34 — Checkout applies partial state before authorization and has no atomic transaction
**High · high confidence source sequence; concurrency effects untested.** `routes/order.ts:78-81` updates inventory before wallet funds are checked at `:148-153`. Insufficient funds therefore returns an error after stock changes, with no rollback. Wallet balance reads and decrements are separate operations; stock read/write is also separate, and order insertion/basket deletion occur later (`:164-180`, `:47-52`). Concurrent checkouts can race on balance/stock or duplicate processing; PDF creation precedes failure and can leave artifacts. Transaction defaults in `models/index.ts:40` do not create a transaction around this handler.

**Remediation:** reserve/validate inventory and funds atomically with conditional updates and transaction boundaries; use idempotent order state transitions and compensating cleanup for files/document-store actions. **Regression:** insufficient funds leaves inventory/basket/wallet unchanged; parallel identical checkout requests produce one order and cannot overspend or oversell; injected failures leave consistent state.

### F35 — Review likes use a race-prone check-then-write sequence
**Medium · high confidence source sequence.** `routes/likeProductReviews.ts:25-38` checks whether a user liked a review, then increments the count separately. It waits 150 ms at `:41` before adding that user at `:43-53`. Parallel requests can each pass the initial check and increment likes multiple times. Updates can also lose other concurrent voters' arrays. Impact is review-ranking integrity, not authorization takeover.

**Remediation:** atomic conditional update with unique per-user vote records or add-to-set plus count derived from those records. **Regression:** concurrent likes by one user increase count once; concurrent distinct voters remain recorded and counted correctly.

### F36 — Public file, configuration and diagnostics routes disclose sensitive material
**High · high confidence routes; contents/state vary.** `server.ts:288-303` publishes directory indexes and file handlers for FTP, encryption keys and support logs without authentication. FTP inventory includes backups, a password database and business documents; filenames alone do not establish their contents. `routes/order.ts:41-45,65-68` writes order PDFs containing customer email and order details directly into that listed FTP directory, and `.pdf` is allowed by `routes/fileServer.ts:56-57`. This makes even unpredictable order IDs discoverable after orders exist. Access logs contain full password-change URLs (F08).

`routes/appConfiguration.ts:11-15` publishes the entire configuration except `llmApiUrl`, reachable anonymously at `server.ts:627`. This includes recovery-answer configuration fields present at `config/default.yml:1053,1058`; actual seeded account binding was not independently inspected. `/metrics` (`server.ts:696,750`, `routes/metrics.ts:84-99,136-155`) discloses runtime/process and aggregate business metrics. `errorhandler()` is enabled unconditionally at `server.ts:702`, so developer error details may be returned, subject to that dependency's response formatting. Public signing-key disclosure is assessed separately in F03.

**Remediation:** authenticated ownership-aware receipt downloads; remove directory listings/backups/key/log files from public roots; explicit public-config schema; restrict diagnostics and use generic production errors. **Regression:** anonymous users cannot list/fetch receipts, logs or private files; safe config contains no recovery inputs; error responses omit stack/query details and metrics require intended access.

### F37 — File validation occurs before canonicalization, with Windows path-separator gaps
**High · high confidence source flow; platform-dependent traversal.** `routes/fileServer.ts:26-32` checks `.md`/`.pdf` suffixes, then cuts the filename at literal `%00` using `lib/insecurity.ts:44-49`, and serves the resulting path. An encoded input that becomes `backup.ext%00.pdf` after route decoding passes the suffix check but serves `backup.ext`. This defeats the intended file-type restriction without needing a real NUL accepted by the OS. The file, key, log and quarantine handlers reject only `/` (`fileServer.ts:17`, `keyServer.ts:13-14`, `logfileServer.ts:13-14`, `quarantineServer.ts:13-14`); on Windows, decoded backslashes can carry traversal into `path.resolve`. No root option or post-resolution containment check is used. Router/proxy decoding and OS behavior must be tested to establish actual read reach beyond each directory.

**Remediation:** reject ambiguous encoding/NUL representations, normalize once, validate canonical names, and enforce real-path containment under a dedicated root; do not rely on extension filters for confidentiality. **Regression:** encoded percent/NUL patterns cannot change the validated target; Windows and POSIX traversal/backslash/absolute path cases stay confined.

### F38 — CAPTCHA answers are returned and challenges are reusable or fail open
**Medium · high confidence.** `routes/captcha.ts:24-31` returns the answer alongside the challenge; verification at `:35-39` neither consumes it nor checks expiry/session binding. Image CAPTCHA also returns its answer (`routes/imageCaptcha.ts:24-31`), and its check permits requests when no recent CAPTCHA exists (`:42-53`). `frontend/src/app/data-export/data-export.component.ts:47-53` decides whether to request a CAPTCHA using editable localStorage. Automated clients can bypass both anti-automation mechanisms without solving an image or equation, and CAPTCHA records accumulate.

**Remediation:** keep answers server-side, bind challenge to session/action, expire and atomically consume it, and enforce challenge requirements server-side. **Regression:** responses omit answers; missing/stale/replayed/foreign challenges fail; localStorage edits do not bypass enforcement.

### F39 — Weak recovery proof and spoofable IP throttling enable guessing
**High · high confidence design; deployment determines IP spoofability.** `routes/resetPassword.ts:35-46` resets a password solely on a reusable knowledge answer, without a one-time recovery token or second-factor check. `routes/securityQuestion.ts:15-25` reveals whether an email has a recovery question. `server.ts:367` trusts every proxy, and reset throttling (`:368-372`) falls back to Express `ip`; Node header keys are lowercased, so the explicit mixed-case `headers['X-Forwarded-For']` is not a robust custom check. With an attacker-controlled forwarded chain at the ingress, the trusted proxy setting permits varying derived IPs. Login has no limiter at `server.ts:616`; MFA endpoints have per-IP limits (`:480-495`) but no per-account attempt state.

**Remediation:** proof of control through expiring, one-time recovery tokens, MFA-aware recovery policy, non-enumerating responses, trusted proxy hop/network configuration and per-account plus IP limits. **Regression:** forwarded-header changes cannot reset an account's budget; recovery without valid one-time proof fails; known/unknown emails have equivalent responses; login/MFA attempts are bounded.

### F40 — Chat authorization trusts unverified JWT payloads
**High · high confidence source authorization bypass; model response unverified.** `server.ts:658` exposes chat without `isAuthorized`. `routes/chat.ts:42-46` decodes a Bearer token and returns `data.id` without verifying signature, expiry or token type. `:158-170` uses that ID to load an email and authorize order retrieval. Global `updateAuthenticatedUsers` does not reject invalid tokens; it simply declines to cache them (`lib/insecurity.ts:184-194`). A forged payload can therefore select another existing user for chat authorization. Retrieving a particular order still requires its ID and a model invocation of the order tool; exact model behavior was not tested. The masked-email issue in F17 further weakens this check.

**Remediation:** reuse verified request identity and immutable owner ID, with tool-layer authorization independent of prompts. **Regression:** forged/expired/wrong-purpose tokens cannot influence username lookup or order-tool ownership; cross-user tool calls fail even when explicitly requested in the conversation.

### F41 — Chat coupon authorization is expressed only in model instructions
**High for commerce integrity · high confidence missing enforcement; model compliance unverified.** `routes/chat.ts:97-104` describes damaged-order, rejection and maximum-discount policies in a prompt (and contains a contradictory courtesy exception). The tool schema at `:174-183` accepts any number and its execute callback generates a coupon without authenticated eligibility, damage proof, order ownership, maximum validation or redemption restrictions. Untrusted username data is inserted into the system prompt at `:81-85`; review/product data and the whole caller-supplied message history (`:189-205`) also reach the model. Prompt injection can influence behavior, but no successful prompt or exact model response is claimed. The missing server checks are deterministic regardless of whether a particular model currently follows the policy.

**Remediation:** enforce discount bounds and eligibility in code against authenticated order/refund state; constrain client roles/history and treat retrieved text as data. **Regression:** invoke the tool callback with over-limit discounts, ineligible users and unrelated orders; every case fails even if the model asks for it. Include indirect prompt-injection cases in a separate model evaluation.

### F42 — Anonymous chat consumes unbounded aggregate model resources
**Medium · high confidence missing controls; requires a configured reachable provider.** `routes/chat.ts:189-211` forwards caller messages to the configured model with up to ten tool steps and retries, but no user quota, rate/concurrency gate, explicit output-token cap or request cancellation budget. `server.ts:658` is public. Express body-size defaults bound individual request bodies, and the ten-step limit is real, but neither limits aggregate provider spend or parallel generation. There is no abort hookup for disconnected clients in the reviewed handler. Public tool-call traces are always streamed at `:218-236` regardless of admin status; the frontend only hides them with a cookie (`chat-conversation.component.ts:64`, `.html:25`). These traces reveal tool names/arguments, not tool result objects, so unrestricted disclosure of all tool output is not claimed.

**Remediation:** authenticated quotas or explicit anonymous limits, bounded input/output, global concurrency and cost budgets, cancellation, and server-side filtering of genuinely privileged traces. **Regression:** concurrent/abandoned requests stay within a provider-call budget; non-admin responses omit trace details intended to be private.

### F43 — Frontend attaches shop credentials to every HttpClient destination
**Medium · high confidence client flow; actual cross-origin delivery unverified.** `frontend/src/app/Services/request.interceptor.ts:12-25` adds the shop token and stored email without checking the request origin. It is globally registered (`frontend/src/main.ts:86-87,120`). `frontend/src/app/Services/user.service.ts:67-68` makes a Google userinfo request through that HttpClient, so a still-present shop token can be attached to the external request. Browser CORS/preflight or provider rejection may stop delivery; this review does not claim a captured token. The pattern also exposes credentials to any future external HttpClient integration.

**Remediation:** attach credentials only to a strict parsed shop/API origin and path allowlist; use a separate provider client. **Regression:** external userinfo and other cross-origin requests never contain shop Authorization or X-User-Email headers, while intended API requests do.

### F44 — Chat history persists across account changes in shared browser storage
**Medium · high confidence · subsequent user of the same browser profile.** `frontend/src/app/Services/conversation-storage.service.ts:9,25-44` stores every conversation under a single origin-wide key without an account namespace. `chat-conversation.component.ts:66-70,91-103` reloads/persists it. Logout (`navbar.component.ts:241-249`) does not clear this store. A later account or unauthenticated person using that browser can read the previous user's conversations, potentially including order details. This is local/shared-browser disclosure, not evidence of remotely reading another browser's storage.

**Remediation:** partition by verified account, clear sensitive local history on logout/account change, or use authorized server storage and deliberate retention controls. **Regression:** account B and a logged-out session cannot load account A's saved conversation IDs or list history.

### F45 — Upload metrics create attacker-controlled label cardinality
**Medium · high confidence · anonymous uploads.** `routes/metrics.ts:27-36,73-78` creates time series labeled with `file.mimetype`, supplied in multipart data. `server.ts:335` observes this for public complaint uploads; `routes/fileUpload.ts:62-68` does not reject arbitrary MIME labels. Repeated small uploads with distinct MIME subtypes can grow the in-process registry and metrics response without a fixed cardinality bound. Prometheus scraping is not required for the application to allocate labels; practical exhaustion was not measured.

**Remediation:** map MIME types to a fixed enum/unknown bucket and apply upload/request quotas. **Regression:** many distinct untrusted MIME labels produce only a bounded number of series and bounded `/metrics` output.

### F46 — Deployment templates allow plaintext authenticated traffic
**Medium · high confidence configuration; deployment unverified.** Both `terraform/networking.tf:157-165` and `infrastructure/terraform/networking.tf:157-165` configure port 80 to forward application traffic instead of redirecting to HTTPS. `vagrant/default.conf:1-6` exposes HTTP proxying. App cookies have no Secure flag (F24), and no HSTS is configured in `server.ts:186-195`. In a deployment following these templates, a user staying on HTTP can expose credentials/tokens to a network observer. The presence of a separate HTTPS listener does not force HTTP clients to upgrade. Local training use over a trusted loopback network has a narrower risk.

**Remediation:** redirect HTTP to HTTPS at ingress, set Secure cookies, and use HSTS once HTTPS deployment is verified; keep training instances isolated. **Regression:** plaintext paths redirect without authenticating or returning sensitive data; secure cookies never travel over HTTP.

### F47 — Web3 wallet claims are not bound to proof of possession
**Low · high confidence · training-state integrity only.** `routes/nftMint.ts:38-45` accepts a body wallet address and consumes a globally observed mint event without a signed challenge. `routes/web3Wallet.ts:15-29` similarly associates arbitrary supplied addresses with later events. Both routes are public (`server.ts:663-665`), and state is global, not per authenticated user. A caller can claim another wallet's observed activity to change shared challenge state. The embedded mnemonic in `routes/checkKeys.ts:10` is training source material; no claim is made that it controls valuable live funds or that these endpoints move funds.

**Remediation:** require a signed, expiring nonce for wallet ownership and bind event attribution to the verified account/wallet; separate shared training state from financial authorization. **Regression:** claiming an address without its signature cannot consume another user's event or credit completion.

### F48 — Public Web3 listener endpoint retains arbitrary addresses indefinitely
**Medium · high confidence · anonymous.** `routes/web3Wallet.ts:10,15-16` adds any supplied walletAddress to a process-global Set before validation or provider setup. Entries are removed only when a matching external event arrives (`:26-29`); there is no size/TTL bound, even if provider setup fails. Arbitrary strings/objects can create retained entries. Repeated requests can cause application memory growth; no resource-exhaustion test was performed.

**Remediation:** validate canonical address strings, authenticate/limit registrations, bound count/TTL and clean up failed registrations. **Regression:** invalid addresses leave no retained state; high-volume unmatched registrations stay within a fixed budget even when the provider is unavailable.

## Additional observations and follow-up checks

These are kept separate from confirmed exploit paths so they do not inflate certainty:

- **Plaintext card data at rest:** `models/card.ts:37-60` stores full card number/name/expiry in SQLite; masked GET responses in `routes/payment.ts:21-35,41-58` do not protect a database disclosure. This training model contains no evidenced real payment integration. A production adaptation should use payment-provider tokens and verify that raw card values never persist or appear in generated POST responses.
- **WebSocket input robustness:** `lib/startup/registerWebsocketEvents.ts:39-49` calls `includes`/`match` on untyped payloads with only null checks. Unexpected object/number input can throw, and the handlers have no local catch. Whether that exception terminates the process depends on the dispatcher/runtime; no crash was tested. Add event schemas, exception containment and bounded event rates. Notification state is global and unauthenticated (`:22-36`), consistent with shared training mode rather than a per-user guarantee.
- **Promotion subtitles are inserted as HTML:** `routes/videoHandler.ts:71` injects raw VTT into a script element. A file-write primitive such as F25 can turn a writable subtitle into persistent script markup, but the precise enabled traversal path, built asset existence and browser parsing were not exercised. Escape closing script sequences or avoid embedding untrusted text in HTML. Range parsing at `:25-38` also lacks explicit range validation/error handling; malformed requests need resilience tests.
- **Legacy dependency verification remains open:** the version pins for JWT, sanitization, YAML, notevil and MarsDB justify a separate resolved-dependency review. No lockfile/node_modules snapshot was installed or advisory database queried. No historical CVE or package exploit is asserted as proven by a version string alone.
- **Infrastructure is a template, not deployment evidence:** the main Dockerfile uses a non-root distroless runtime (`Dockerfile:22,38-41`); the alternative infrastructure image also uses a non-root user (`infrastructure/Dockerfile:21`). The alternative refers to missing/unchecked build artifacts and a Node version different from `package.json`'s engine range. Compose defines Redis/Mongo, but application collections use in-process MarsDB and SQLite; this review does not infer a networked Mongo injection target from Compose alone. Cloud IAM/EFS/TLS resources were not applied, certificates and network exposure were not validated, and no host/container escape was attempted.
- **Safety mode is not a complete security control:** disabling gated branches does not repair ungated authentication, generated API authorization, chat, export rendering, disk upload ordering, or static secret exposure. It is inappropriate to treat `safetyMode: enabled` as a production-hardening guarantee.

## Recommended repair sequence

1. Isolate the intentionally vulnerable deployment and eliminate publicly accessible signing/recovery secrets and sensitive file/DTO disclosures; rotate affected credentials.
2. Replace raw queries/evaluation and unsafe parsing/extraction. Centralize complete token verification, session revocation, operation authorization and owner-scoped data access.
3. Replace unrestricted generated writes with explicit schemas and business commands; enforce positive quantities, authorized payment state and atomic/idempotent checkout.
4. Remove HTML trust bypasses and JSON-as-HTML rendering; harden cookie/CSRF policy and isolate uploads.
5. Enforce chat tool identity/policy in code and bound expensive processing, storage, metrics cardinality and provider usage.

Regression checks should use isolated synthetic fixtures and two-account authorization matrices, not the challenge-solved flags. For each fix, exercise the registered HTTP route as well as the lower-level helper so route ordering and generated API behavior are covered. Browser checks are required for XSS/CSRF/CSP/JSONP; concurrency and failure injection are required for checkout/likes. None were executed in this review.
