# WebGoat and WebWolf — source-only security review

Reviewed checkout: `C:\Users\User\Projects\web-security-audit-workspace\webgoat`. Review date: 2026-10-29. The application was not started, built, or exercised. No deployed services, external URLs, dependency advisories, historical reports, separate answer keys, or audit skills were consulted. This report describes this checkout, not an upstream release generally.

The lessons deliberately teach exploitation. Their vulnerable code is inventoried separately from shared platform defects. An exercise invoking an operating-system command is an intentional mechanism; allowing it to share the platform's OS identity and data is a containment issue. Severity below assumes a reachable instance used by multiple people. A disposable single-user installation has less cross-user impact, but host filesystem access still matters.

Evidence uses repository-relative `path:line` anchors. **J** means `src/main/java/org/owasp/webgoat/`, **L** means `src/main/java/org/owasp/webgoat/lessons/`, and **R** means `src/main/resources/`. These are literal path substitutions. `process.md` records individual reads and limitations. “Source proven” means a data/control-flow property is visible, not that a runtime exploit was executed. Regression checks below are recommendations, not tests performed.

## 1. Platform findings: container, server, WebWolf, configuration, and templates

### P01 — A known administrator password is restored on startup (High)

**Evidence/root cause:** `J/container/users/DefaultUserInitializer.java:25` defines administrator `webgoat-admin`, and line 27 defines password `webgoat`. The runner at lines 33–44 saves a newly constructed administrator even when the account exists. A default ordinary account is added at lines 52–55. This is real platform administration: `J/container/WebSecurityConfig.java:53` requires `WEBGOAT_ADMIN`; `J/container/users/AdminController.java:55`, `:84`, and `:159` expose user/progress administration and password reset under administrator checks.

**Impact/bounds:** Anyone who can reach login can use source-known credentials after startup. The administrator can inspect progress and reset platform passwords. Changing the administrator password does not survive another initializer run. Network reachability was not tested; loopback-only is not automatically Internet-exposed.

**Remediation:** Make bootstrap explicitly opt-in for a disposable training profile; otherwise require a supplied/random initial secret, create only if absent, and never overwrite an existing password. **Regression:** Change the admin password, restart, verify the old default fails and the new password works; verify ordinary/anonymous users cannot use admin APIs.

### P02 — Shared platform credentials are stored in plaintext (High)

**Evidence/root cause:** `J/container/WebSecurityConfig.java:97` and `J/webwolf/WebSecurityConfig.java:85` supply `NoOpPasswordEncoder`. `J/container/users/UserService.java:47` persists the supplied password and `:99` persists reset passwords unchanged. `J/container/users/WebGoatUser.java:25`–39 contains the plain password field. `R/db/container/V1__init.sql:45` defines the user table, which WebWolf also reads. Registration limits passwords to ten characters (`J/container/users/UserForm.java:23`).

**Impact/bounds:** A shared database/backup read immediately reveals reusable WebGoat/WebWolf login credentials; P03 supplies an in-application path worth prioritizing. Lesson fixture passwords are not asserted to be real external credentials. Plaintext use is explicitly documented in the code, but affects the shared platform.

**Remediation:** Use adaptive salted hashes in both applications, migrate existing records, and permit long passphrases. Keep intentionally weak examples in separate fixtures. **Regression:** Register/reset an account, confirm neither database value equals its password, and verify both applications authenticate it; test migration and long passwords.

### P03 — Per-user schemas do not isolate injectable SQL from platform tables (High)

**Evidence/root cause:** `J/container/DatabaseConfiguration.java:30`–64 supplies the same underlying data source to container and lesson migrations. `J/container/LessonDataSource.java:26`–32 wraps that source's connection; `J/container/lessons/LessonConnectionInvocationHandler.java:31` changes only its current schema. `J/container/users/UserService.java:78` creates lesson schemas with `authorization dba`. Exercises intentionally execute entire submitted SQL statements, including `L/sqlinjection/introduction/SqlInjectionLesson3.java:41` and `SqlInjectionLesson4.java:39`–40.

**Impact/bounds:** Current schema is name resolution, not authorization. No per-student database identity/grants are established in this path. Qualified references to other schemas, including `CONTAINER`, run under the application's identity. Accounts, mail, progress, and other students' fixtures are at risk if those grants permit the operation; common privileged startup DDL strongly supports the concern. Actual HSQL grants, cross-schema execution, database filesystem features, and rollback behavior were not tested. This is not proof of database-to-OS execution.

**Remediation:** Separate platform and injectable lesson databases; use per-student disposable databases or genuinely restricted identities. **Regression:** A lesson connection must fail to read/update platform user/mail/progress tables, another student's schema, or administrative grants while its intended exercises still work. Verify using the actual database engine and configuration.

### P04 — Real host-level lesson sinks share the platform's identity (High containment risk)

**Evidence/root cause:** `J/server/StartWebGoat.java:20`–35 starts both applications in one JVM. `L/commandinjection/CommandExecutionService.java:27`–30 selects `/bin/sh -c` or `cmd.exe /c`; line 65 starts the process, with inherited/extended environment at line 55. Traversal lessons write outside nominal exercise paths, and deserialization/XML sinks appear in section 3. No OS sandbox is established by those call paths. The command safety acknowledgment is consent to a lesson, not isolation.

**Impact/bounds:** A student running these lessons can affect data accessible to the Java process, potentially including shared platform files. Actual access is bounded by OS permissions, mounts, identity, and network policy. The non-root Docker user reduces privilege but does not isolate students. The command runner has a five-second wait and 64 KiB output cap (`CommandExecutionService.java:17`–18) plus process-tree cleanup: useful limits, not a sandbox. No host takeover/container escape was demonstrated.

**Remediation:** Put dangerous lesson execution into disposable per-user workers with separate identities, restricted mounts/network, no platform secrets, and read-only application files. Preserve the teaching mechanism inside that boundary. **Regression:** Verify a worker cannot access platform files, other students' storage, or disallowed destinations, and cannot leave processes running after its deadline.

### P05 — Anonymous mail ingestion reaches unescaped platform HTML (High)

**Evidence/root cause:** `J/container/WebSecurityConfig.java:50`–51 permits anonymous `POST /mail`. `J/container/mailbox/MailboxController.java:58`–64 accepts/saves attacker-selected recipient, sender, title, and contents. `R/webgoat/templates/mailbox.html:142` renders `mail.contents` with `th:utext`. Recipient filtering on GET (`MailboxController.java:38`) does not authenticate the sender or sanitize contents.

**Impact/bounds:** An unauthenticated sender can plant HTML in a chosen user's platform mailbox. Viewing it can execute script with that WebGoat user's origin/session, with greater impact for an administrator victim. The unsafe source-to-sink path is explicit; browser execution and any external proxy CSP were not tested. This is separate from the XSS lesson.

**Remediation:** Prefer internal mail service calls; otherwise authenticate producers and constrain recipients. Render text or sanitize the narrow HTML needed for lesson links. JSON escaping is not HTML sanitization. **Regression:** Reject anonymous delivery; render event handlers/closing tags harmlessly while preserving valid instructional links, including in the admin mailbox.

### P06 — Any authenticated user can delete all users' mail (High integrity/availability)

**Evidence/root cause:** `J/container/mailbox/MailboxController.java:67`–70 maps `DELETE /mail` to repository-wide `deleteAll()` without principal, recipient filter, or admin check. The global rule requires only authentication (`WebSecurityConfig.java:55`–56).

**Impact/bounds:** A registered student can erase every mailbox's records, including lesson/reset mail. This does not directly delete accounts/progress. **Remediation:** Delete only the current recipient's messages, or require admin authorization for an explicit global purge; also require CSRF protection. **Regression:** Deleting as Alice leaves Bob's messages intact; non-admin global purge is denied.

### P07 — Mail binds an unvalidated persistence entity, enabling poisoning and possible row replacement (Medium)

**Evidence/root cause:** Public delivery binds the JPA entity (`MailboxController.java:60`). `J/container/mailbox/Email.java:28`–30 exposes generated `id` without the JSON exclusion used for `time`/`read` at lines 32/45. Its `getSummary()` dereferences contents at line 50; `getShortSender()` assumes a non-null sender containing `@` at line 62. `R/webgoat/templates/mailbox.html:132`–134 invokes both. No recipient-existence, null validation, message-count quota, or delivery throttling appears in this controller.

**Impact/bounds:** Persisted malformed mail can break a recipient's mailbox view; repeated public delivery consumes shared storage. The contents column is limited to 1,024 characters, so this is not an unlimited single-message claim. A supplied existing ID may cause JPA `save` to merge/replace a record and redirect its recipient: that is an identified mass-assignment path needing confirmation on the actual Jackson/Hibernate versions, not a demonstrated overwrite. Poisoning/storage concerns do not rely on that hypothesis.

**Remediation:** Use a validated delivery DTO without persistence IDs, construct new entities server-side, make getters robust, and enforce quotas/retention. **Regression:** Null content, bad sender, unknown recipient, and a supplied existing ID must be rejected or safely normalized without modifying other mail; malformed legacy rows must not break rendering.

### P08 — WebWolf upload filenames escape the user's directory (High)

**Evidence/root cause:** `J/webwolf/FileServer.java:86` creates a user directory, but line 91 resolves the multipart original filename without containment validation; lines 92–93 delete the destination then copy bytes. POST upload requires authentication: `J/webwolf/WebSecurityConfig.java:38`–43 permits GET, not POST. `R/application-webwolf.properties:40`–41 limits file/request size to 1 MB.

**Impact/bounds:** A registered user controlling the raw multipart filename can use traversal/absolute paths to overwrite or delete Java-process-writable files, including another user's uploads and potentially platform data. Parent directories must exist; platform path rules differ. Code execution needs a useful writable target and later execution and is not established here. The size limit does not prevent small destructive overwrites. The upload root is disclosed to authenticated callers by `FileServer.java:63`–69.

**Remediation:** Use generated storage names, separately validate display names, normalize/verify containment and symlink behavior, and never delete an unvalidated destination. **Regression:** Test traversal, mixed separators, drive/UNC paths, absolute names, symlinks, and existing other-user files. No file outside the allowed root may change; normal uploads must succeed.

### P09 — WebWolf hosts attacker-authored active content on its management origin (High containment risk)

**Evidence/root cause:** `J/webwolf/FileServer.java:72`–93 accepts arbitrary types; `J/webwolf/MvcConfiguration.java:25` serves `/files/**` from that location; `WebSecurityConfig.java:38`–43 makes GET public. These paths impose no separate origin or forced download. Hosting files “as an attacker” is the intended feature (`R/webwolf/templates/files.html:22`).

**Impact/bounds:** If a file is served as active HTML/SVG, opening it can run script with the WebWolf origin and access management pages/actions using the viewer's session. Public hosting is intentional; origin sharing is the containment weakness. Different default WebGoat/WebWolf ports mean different origins, so this alone does not grant script read access to WebGoat. MIME/browser behavior was not tested. Listing labels and upload messages use `th:text` (`files.html:15`, `:65`); they are not a filename-listing XSS.

**Remediation:** Serve lesson payloads from a separate cookieless origin with no management APIs. Use download disposition where execution is unnecessary. **Regression:** An uploaded active page cannot read management data or invoke authenticated APIs as its viewer; intended isolated attacker-hosting still works.

### P10 — WebWolf captured requests are rendered as executable HTML (High)

**Evidence/root cause:** `J/webwolf/requests/WebWolfTraceRepository.java:68`–72 records non-excluded requests without verifying WebGoat origin. Landing GETs are anonymous. `J/webwolf/requests/Requests.java:76`–78 serializes exchanges as JSON; `R/webwolf/templates/requests.html:47` inserts that string with `th:utext`, and line 39 inserts path unescaped. JSON serialization does not stop an HTML parser recognizing tags in strings. Request-header recording is configured at `R/application-webwolf.properties:32`.

**Impact/bounds:** HTML in a captured header can execute when a user opens the request dashboard; the header route does not require the server to accept angle brackets in a URL. P11 broadens the audience. Unsafe rendering is source proven; actual Boot recording activation and browser execution need runtime checks. The repository has a 10,000-record cap (`WebWolfTraceRepository.java:45`).

**Remediation:** Use `th:text`/text nodes for JSON, paths, and dates, including inside `pre`; add management CSP and per-user callback channels. **Regression:** Captured HTML, event handlers, and closing `pre` tags appear literally with no active nodes, while ordinary JSON remains readable.

### P11 — WebWolf trace ownership defaults to allow and includes session-bearing headers (High, recording-dependent)

**Evidence/root cause:** `J/webwolf/requests/Requests.java:47` reads the global trace list. `allowedTrace()` starts true at line 58 and only conditionally excludes `/files` and `/landing?...uniqueCode...` with substring comparisons at lines 60–65. Ordinary landing/other routes remain visible to all authenticated viewers. `WebWolfTraceRepository.java:47`–56 does not exclude login/upload and all authentication-related paths. `R/application-webwolf.properties:32` includes `COOKIE_HEADERS`, request headers, and response headers.

**Impact/bounds:** Captured URLs/headers can disclose other users' lesson reset tokens or session cookies to a logged-in student; overlapping usernames/codes weaken substring ownership further. This is not a claim of POST-body password logging: exchange metadata is recorded, not bodies. Actual Cookie/Set-Cookie retention under the selected framework version was not exercised. Default-allow ownership is explicit independent of that detail.

**Remediation:** Bind callbacks to opaque owner-specific channels, deny unowned records, compare exact identifiers, and redact secrets before storage. Collect intended callbacks only. **Regression:** Test two users, overlapping names, unknown channels, and login/upload exchanges; neither other-user records nor cookies/authorization values may appear in the repository/dashboard.

### P12 — CSRF is disabled for management, and destructive lesson reset uses GET (High when privileged sessions are targeted)

**Evidence/root cause:** `J/container/WebSecurityConfig.java:71` and `J/webwolf/WebSecurityConfig.java:47` disable CSRF globally. `J/container/users/AdminController.java:159`–168 resets actual platform passwords. `J/container/service/RestartLessonService.java:35` maps a state-changing GET; lines 41–49 reset progress, clean/migrate the user's lesson schema, and reinitialize lessons. The client calls GET at `R/webgoat/static/js/goatApp/controller/LessonController.js:139`–140.

**Impact/bounds:** Attacker pages can attempt actions with a victim's ambient session; an admin reset affects real credentials. SameSite, content type, and origin determine which requests deliver cookies. Top-level navigation to a destructive GET is relevant even with Lax cookies. Different ports are different origins but normally the same site. No live browser CSRF was tested; CORS/SameSite alone is not adequate evidence of protection.

**Remediation:** Enable CSRF for platform routes, isolate deliberate lesson exceptions, and make destructive operations non-GET with tokens. **Regression:** GET/HEAD cannot reset state/passwords; missing/invalid tokens fail for admin, mailbox deletion, uploads, and real account flows; exercise exemptions do not encompass management paths.

### P13 — A username prefix redirects grading writes to another user (Medium)

**Evidence/root cause:** `J/container/assignments/LessonTrackerInterceptor.java:54` obtains the real principal, but `realUsername()` strips `csrf-` at lines 73–77 before progress lookup/write at lines 58–70. Public registration permits lowercase letters/digits/hyphens (`J/container/users/UserForm.java:17`–20); `UserValidator.java:24`–33 does not reserve the prefix.

**Impact/bounds:** An available `csrf-<victim>` registration can submit results attributed to the victim. Username length bounds eligible names. This changes grade/attempt records, not general login identity or passwords. **Remediation:** Bind progress to an immutable authenticated ID; represent simulated CSRF victims in lesson state, not public username syntax. **Regression:** Register Alice and a prefixed account, submit successes/failures as the latter, and verify Alice's progress does not change.

### P14 — Credential lookup destructively initializes lessons before password checking (Medium)

**Evidence/root cause:** `J/container/users/UserService.java:39` invokes every lesson initializer from `loadUserByUsername()` before returning credentials. `L/webauthn/WebAuthnLessonState.java:96`–99, for example, removes the user's lesson state. `J/container/WebSecurityConfig.java:80`–81 registers this service for authentication.

**Impact/bounds:** In the configured Spring provider flow, lookup precedes password comparison. A failed login for a known username can reset their lessons, including simulated security keys. Direct destructive lookup is source proven; exact provider caching/timing was not exercised. This is state disruption, not password-verification bypass. **Remediation:** Keep credential lookup read-only; initialize after successful login and distinguish first-time initialization from reset. **Regression:** Failed logins/lookup leave populated state unchanged; successful login preserves state unless reset is explicitly requested.

### P15 — OAuth-completion GET overwrites an existing local account (Medium)

**Evidence/root cause:** `J/container/users/RegistrationController.java:61`–66 accepts any authenticated principal at `/login-oauth.mvc` and calls `addUser(name, randomUUID)`. `UserService.java:46` checks existence but line 47 saves a new account regardless; its constructor defaults to ordinary role (`WebGoatUser.java:32`–39). Existence only gates lesson creation.

**Impact/bounds:** A local logged-in user visiting this GET replaces their stored password with an unknown random value; an admin loses its stored admin role. Cross-site navigation can trigger it when session cookies are sent. Configured OAuth-name collisions also risk improper account linking, but provider mapping/live OAuth was not verified and default client credentials are placeholders. Arbitrary remote account takeover is not established.

**Remediation:** Restrict completion to validated OAuth authentication, identify users by provider plus stable subject, and explicitly prove ownership when linking accounts. Do not replace passwords/roles on GET. **Regression:** A local session cannot change credentials through this route; colliding external display names cannot overwrite accounts; repeat OAuth login is idempotent.

### P16 — Public Actuator metadata and detailed errors (Medium)

**Evidence/root cause:** `J/container/WebSecurityConfig.java:45`–46 permits `/actuator/**`. `R/application-webgoat.properties:80`–82 exposes env/health/configprops and always shows detailed DB health. Line 1 configures error stacktrace inclusion. WebWolf has a legacy stacktrace property (`R/application-webwolf.properties:1`), but its HTML error template only shows escaped date/path/status (`R/webwolf/templates/error.html:25`–33).

**Impact/bounds:** Reachable WebGoat management/error responses may reveal operational metadata and implementation details. Do not infer cleartext environment secrets: framework masking/show-values defaults may hide them. Do not claim WebWolf's HTML template prints stack traces; it does not. WebWolf management HTTP is separately disabled at `application-webwolf.properties:12`. Availability, JSON error negotiation, sanitization, and legacy-property aliases need runtime checks.

**Remediation:** Publish minimal health only, authenticate/restrict management, and disable detailed errors outside diagnostic profiles. **Regression:** Anonymous env/configprops/detailed health are denied; HTML/JSON errors contain safe correlation information, and authorized diagnostics mask secrets.

### P17 — WebGoat disables default security headers for management pages too (Medium defense-in-depth)

**Evidence/root cause:** `J/container/WebSecurityConfig.java:72` disables the entire security-header configuration, including normal frame/content-type defenses. No platform-wide replacement was identified in reviewed config. WebWolf does not contain the same call.

**Impact/bounds:** Management pages lose defenses against framing/content confusion and existing injection paths have fewer barriers. This alone does not prove compromise; a deployment proxy may add headers. **Remediation:** Restore defaults and a management CSP/frame policy; scope unsafe teaching behavior to explicit lesson origins/profiles. **Regression:** Assert chosen frame/nosniff/cache/CSP protections on management responses and verify admin UI cannot be driven in an external frame.

### P18 — Lesson exclusion hides navigation, not vulnerable controllers (Medium deployment-control weakness)

**Evidence/root cause:** `R/application-webgoat.properties:74`–78 exposes category/lesson exclusions. `J/container/service/LessonMenuService.java:57`–70 only skips menu entries. `J/container/WebGoat.java:22` scans lesson components; `CourseConfiguration.java:86`–97 attaches all injected assignments. These exclusion values are not sink authorization.

**Impact/bounds:** Hiding command/SQL/deserialization lessons does not prevent direct authenticated requests. The setting may intentionally be a UI filter: the finding is its inadequacy as a security-disable control, not broken menu filtering. **Remediation:** Clearly name/document UI-only filtering; for actual disabling, conditionally register controllers or enforce enabled-lesson policy before dispatch. **Regression:** Direct requests to all disabled-lesson routes must fail without reaching sinks when a security policy disables the lesson.

### Deployment observations and counterevidence

`R/application-webgoat.properties:6` and `R/application-webwolf.properties:8` default to loopback. The standard Docker entrypoint passes `--server.address=0.0.0.0` and exposes two ports; host publication/firewalls determine reachability, so “public Internet by default” is not established. TLS is disabled by default (`application-webgoat.properties:16`); the optional bundled keystore has a known password at line 14. Use independently managed keys/certificates for real TLS. The keystore was not opened/extracted. Plain HTTP on a shared non-loopback network exposes login/session traffic, but no interception was tested.

`Dockerfile:12` switches to non-root, reducing OS privilege without per-student isolation. Admin authorization annotations are present; these endpoints are not labeled anonymous just because the application contains vulnerable lessons. Different ports, schema naming, safety acknowledgment, and menu filtering are incomplete boundaries.

No external dependency/CVE assessment was performed. Dependency observations are tied to actual source sinks rather than unverified advisory matches. Reviewed template resolvers load classpath resources, and selected lessons come from known course entries; a remote arbitrary template-name path was not established. Public static resources alone do not establish arbitrary filesystem reading.

## 2. Challenges-package findings

`L/challenges/` is deliberately vulnerable exercise logic. Challenge logins, PINs, flags, vote board, and reset actions are not platform authentication. This checkout has implemented challenge directories **1, 2, 5, 7, and 8**. Numbered images/resources and flag-map slots 1–9 do not establish live controllers for missing numbers. `SolutionConstants.java` and the downloadable `.git` archive were not opened.

### C01 — Challenge 1 embeds a short shared PIN in a downloadable image (Intended; exercise authentication bypass)

`L/challenges/challenge1/ImageServlet.java:17` chooses a PIN with `Random` in a 10,000-value range; lines 24–37 load a packaged image and overwrite byte offsets 32–35 with it before returning the image. `Assignment1.java:27` hardcodes the IP-allow condition to true; lines 29–34 compare the exercise identity/password/PIN and release the flag. The exposed image is the concrete secret-disclosure sink, not an arbitrary file-read endpoint. The PIN is shared controller state, not per-user authentication state.

**Bounded impact:** Obtaining/reusing the image PIN bypasses this exercise's check; it does not log into WebGoat administration. **Production remediation:** Never transmit a secret inside a public asset; use a cryptographic, per-session, expiring challenge and genuine server-side policy. **Regression:** Public image bytes must not reveal an authentication secret; another user's or expired challenge cannot authenticate; an IP policy must actually evaluate its configured source.

### C02 — Challenge 5 concatenates the password into a prepared SQL statement (Intended SQL injection)

`L/challenges/challenge5/Assignment5.java:35` fixes/validates the expected username, but lines 40–46 construct SQL by concatenating the submitted password before calling `prepareStatement()` and `execute()`. Preparing an already-concatenated string does not parameterize it. The injectable input is the password, not an arbitrary allowed username.

**Bounded impact:** The intended consequence is exercise-login/flag bypass and access permitted by the lesson connection. Shared database privileges in P03 can enlarge the real impact; no OS execution is established. **Remediation/check:** Bind values as parameters and restrict database identity. Assert quotes/SQL operators in the password are literal data and cannot authenticate or access other schemas.

### C03 — Challenge 7 uses a deterministic, reusable reset capability and exposes a repository archive (Intended secret disclosure/reset weakness)

`L/challenges/challenge7/PasswordResetLink.java:7`–12 derives reset material using predictably seeded `Random`, a supplied fixed key, and MD5. `Assignment7.java:32` stores the accepted administrator reset link as a source constant; lines 56–64 compare it and return the flag. The code has no expiry or consumption. Lines 96–99 deliberately serve a packaged `.git` archive; its contents were not opened, so this report does not assert which historical secrets are in it.

**Bounded impact:** Knowledge/prediction/replay of that capability yields the challenge flag. Despite its method name, this controller does not reset a platform account password. **Remediation:** For real reset flows, use cryptographically random, scoped, expiring, single-use tokens and remove repository artifacts from published assets. **Regression:** Tokens differ across requests/users, expire, fail after use, and no source archive is downloadable outside the deliberately isolated exercise.

### C04 — Challenge 7 trusts the request host when producing reset links (Intended link poisoning)

`L/challenges/challenge7/Assignment7.java:77` reads the request URL; lines 81–85 incorporate its scheme/host into an HTML reset link, while the destination mailbox is derived from submitted email at lines 75/87. The mail is sent to the configured mailbox endpoint at line 90, not fetched from the attacker-selected host.

**Bounded impact:** Where proxy/HTTP host validation permits a chosen host, the recipient receives a link pointing there. This is reset-link poisoning/phishing, not arbitrary server-side HTTP fetching. Runtime proxy validation was not examined. P05 explains why mail HTML requires separate controls. **Remediation/check:** Build links from a trusted configured public base URL; vary Host/forwarded headers in tests and verify the generated destination stays fixed. Scope recipients to the intended exercise user.

### C05 — Challenge 8 checks only GET inside a GET mapping (Intended method-based authorization bypass)

`L/challenges/challenge8/Assignment8.java:36` maps GET, but its check at line 41 rejects only requests whose actual method string equals `GET`. The other branch mutates the shared votes at lines 46–47 and returns the flag in a response header at line 49. Spring MVC normally maps HEAD to GET handlers: that framework behavior gives HEAD a path around the method-string check while preserving a header response. This inference was not runtime-tested. The mapping does **not** establish arbitrary POST/PUT support.

**Bounded impact:** Mutation of the synthetic vote board and disclosure of the exercise flag. The static `HashMap` at line 24 is shared between students, accepts unrestricted integer categories, and has unsynchronized read/update iteration; this creates cross-user/race integrity problems within that board, not platform admin access. **Remediation:** Use real authorization independent of method strings; make reads safe and writes POST with CSRF, validate category bounds, and scope/concurrently update state. **Regression:** GET/HEAD do not mutate or disclose privileged flags; unsupported verbs fail; out-of-range votes fail; users' boards and concurrent updates remain isolated/consistent.

### C06 — Challenge 2 models an XML-to-redirect privileged internal fetch, but the dispatcher is bounded (Intended confused-deputy chain)

`L/challenges/challenge2/FeedImportEndpoint.java:23`–28 passes submitted XML to `ChainedXmlService`. Its parser enables general external entities at `ChainedXmlService.java:55`, installs its own resolver at lines 63–65, and passes each system ID to `ChainedFetchService.fetch()` at line 85. The fetched string is returned through a `StringReader` at line 92. `ChainedFetchService.java:57`–62 allows an initial feed or redirect path, but after following `/go` it permits `/internal/diagnostics`; line 48 invokes the diagnostic Java method using the session's internal token. Thus an untrusted redirect causes the importer to use its privilege on a route unavailable as a starting feed.

**Important limits:** There is **no real HTTP client or file read** in `ChainedFetchService`. It dispatches only three fixed lesson paths to Java methods. It rechecks origin on every hop (line 35), only accepts HTTP(S), rejects missing hosts/userinfo/fragments (lines 86–100), caps URL length at 4,096 and redirects at four (lines 18–19). XML length is at most 4,096 and external entity resolution at most four (`ChainedXmlService.java:19`–20); external parameter entities/DTD/schema access are disabled at lines 56–59, with secure processing enabled. Therefore this source does **not** prove arbitrary network SSRF, local-file XXE, unrestricted redirects during import, or cloud metadata access.

`InternalDiagnostic.java:21`–27 checks a session token; it is not simply an anonymous flag dump. `Challenge2State.java:12`, `:22`–25 and `:36`–41 keep a secure random internal token and completion in session scope. `Assignment2.java:21`–24 checks both completion state and the session flag. The boundary bypass is within the intentional virtual lesson, not a global platform flag service.

**Remediation/check:** In a production importer, disable entities and apply destination authorization on every redirect, never automatically attaching internal credentials to an untrusted destination. For this bounded simulator, preserve limits and explicitly test that off-origin/file URLs and excess entities/redirects fail; direct diagnostic access without the token fails; one session cannot claim another's flag. A hardened variant must reject the internal route even after redirect.

### C07 — Challenge 2's separately mapped redirect is an actual open redirect (Intended)

`L/challenges/challenge2/NorthstarEndpoints.java:13`–16 constructs a redirect `Location` directly from submitted `url`. While the virtual import dispatcher checks origin at each hop, a browser calling this controller receives the external destination itself. **Impact:** Phishing/trusted-link redirection within an authenticated lesson, not arbitrary server-side fetching. **Remediation/check:** Use fixed destination IDs or canonical same-origin allowed routes; assert an external URL cannot become Location while approved relative destinations work.

### C08 — Generic challenge flags are process-global, not user-bound (Low grading integrity)

`L/challenges/Flags.java:11`–18 generates one map of UUID flags for slots 1–9. `FlagController.java:26`–34 accepts the matching shared flag, with a special case for challenge 8. Thus a student who learns a flag can share it for another student's completion. This does not disclose the flags without first learning them and does not grant platform authentication. Challenge 2's separate session-bound implementation is stronger and should not be generalized into this finding.

**Remediation/check:** If individual assessment matters, bind challenge capabilities and completion to user/session plus challenge. Alice's flag must fail for Bob, invalid challenge indices should fail cleanly, and restart/session semantics should be explicit. If collaborative flag sharing is intentional, document it instead of treating these grades as individual proof.

## 3. Lesson inventory: actual sinks, mechanisms, and limits

### Cross-cutting lesson limitations and preservation strategy

Most exercise results are returned through `AttackResult` and then rendered as HTML. This is why SQL error text, echoed commands, log-looking output, feedback arguments, and fixture labels deserve encoding review even when their primary lesson topic is unrelated to XSS. Do not use the common renderer as proof that every exercise is cross-user: current-user/session maps and the ability to cause a victim to submit/view data matter. Conversely, a per-user map is not an OS/database boundary.

A useful remediation order is: protect shared administrator bootstrap and mailbox; isolate database/process sinks; separate WebWolf payload hosting from its dashboard and fix trace ownership/encoding; then enforce platform CSRF and identity mapping. Preserve deliberate exercises within per-user disposable boundaries. Regression suites should distinguish an exercise's expected vulnerable demonstration from a prohibited effect on platform accounts, another student's data, host files, or external systems.
